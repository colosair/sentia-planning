# SENTIA 현실 연결부 및 현장 안전관리 직무 기반 설계 — 세션 정본

> 작성 범위: 본 세션에서 논의된 모든 내용
> 
> 핵심 주제: **어떤 데이터를 어떻게 수집·가공할 것인가, 주요 시연을 어떤 실환경에서 진행할 것인가, 그리고 이를 실제 건설현장 안전관리 직무에서 역산해 정의하는 방법**

---

## 0. 세션의 출발점

사용자는 현재 SENTIA 프로젝트에서 아직 미확정인 핵심 영역을 다음과 같이 정의했다.

- 어떤 데이터를 수집할 것인가
- 데이터를 어떤 방식으로 수집할 것인가
- 수집된 데이터를 어떻게 가공할 것인가
- 주요 시연 타이밍에는 어떤 실제 환경을 사용할 것인가
- 즉, 프로젝트 내부 기술 구조와 **실제 세상(real world)** 사이의 연결부가 아직 확정되지 않았다.

초기에는 이를 단순한 데이터셋 선택 문제로 보기보다, 현실 입력과 시스템 사이의 경계 문제로 해석했다.

---

# 1. 초기 접근: Reality Interface Layer

초기 제안에서는 프로젝트의 현실 연결부를 별도의 **Reality Interface Layer**로 정의했다.

```text
[REAL WORLD]
 CCTV / 사진 / 영상 / 센서 / 도면 / BIM / 작업일지 / 작업자 정보
                     │
                     ▼
┌─────────────────────────────────────┐
│       Reality Interface Layer       │
│                                     │
│  Ingest → Normalize → Synchronize   │
│      → Validate → Eventize          │
└─────────────────────────────────────┘
                     │
             표준화된 Observation
                     ▼
┌─────────────────────────────────────┐
│          AI Pipeline                │
│ Detect → Track → Judge → Aggregate  │
│          → Confidence               │
└─────────────────────────────────────┘
                     │
              표준 Event
                     ▼
[BE / Queue / DB / Monitoring]
                     │
                     ▼
[2D/2.5D Digital Twin]
                     │
          ┌──────────┴─────────┐
          ▼                    ▼
       Report               Unreal
                           Extension
```

초기 관점에서 이 레이어가 해결해야 할 문제는 다음 세 가지였다.

1. 무엇을 수집할 것인가
2. 수집된 데이터를 어떻게 가공할 것인가
3. 어떤 현실 환경에서 시연할 것인가

---

# 2. 초기 데이터 수집 범위 제안

처음에는 8주 프로젝트의 범위 관리를 위해 건설현장의 모든 정보를 디지털 트윈화하지 않고, 관측원(Source)을 제한해야 한다고 제안했다.

| 계층 | MVP 권장 | 이후 확장 |
|---|---|---|
| 영상 | CCTV / 고정 카메라 영상 | 다중 CCTV, 이동형 카메라 |
| 이미지 | 현장 촬영 이미지 | 드론 / 정기 촬영 |
| 공간 | 2D 도면 + Zone 정의 | BIM / IFC, 3DGS, Unreal |
| 이벤트 | 안전모 미착용, 인원/객체, 위험구역 진입 등 | 균열, 화재, 중장비, 공정 이상 |
| 환경 센서 | MVP에서는 가짜 Adapter 가능 | 온습도, 진동, 가스, IoT |
| 작업 데이터 | 최소 메타데이터 | 공정표, 작업자, 장비, 작업일지 |

특히 초기 MVP에서 센서 실장비까지 모두 연결하는 것은 위험하다고 판단했다.

센서와 입력원을 아래와 같이 Adapter 뒤에 감추는 구조를 제안했다.

```text
CameraAdapter
FileVideoAdapter
ImageAdapter
SensorAdapter
SimulationAdapter
ReplayAdapter
```

이 구조에서는 AI 이후의 시스템이 입력이 실제 센서인지, 녹화 영상인지, 시뮬레이션인지 알 필요가 없도록 한다.

# 3. 초기 데이터 가공 구조: Observation → Detection → Event → Incident

초기 제안에서는 raw 영상을 AI에 넣고 결과를 바로 BE로 전달하는 구조를 피하고, 중간 단계의 의미 계층을 분리해야 한다고 보았다.

예시:

```text
Frame
 ↓
Observation
{
  sourceId: CAM_03
  timestamp: ...
  zoneId: B-12
}
 ↓
Detection
{
  type: PERSON
  bbox: ...
  helmet: false
  confidence: 0.91
}
 ↓
Event
{
  type: PPE_VIOLATION
  zone: B-12
  confidence: 0.91
  duration: 4.2 sec
}
 ↓
Incident
{
  severity: WARNING
  reason: "안전모 미착용 지속 감지"
}
```

이 구분에서:

- **AI 모델**은 Detection을 생성
- **AI Pipeline**은 Detection을 현장 의미가 있는 Event / Incident로 변환

하는 역할을 가진다고 정리했다.

AI Pipeline에서 담당할 수 있는 기능은 다음과 같이 제안했다.

```text
모델 결과 수신
    ↓
confidence filtering
    ↓
temporal smoothing
    ↓
중복 제거
    ↓
tracking / 동일 객체 결합
    ↓
zone mapping
    ↓
event persistence 판단
    ↓
복수 모델 결과 조합
    ↓
severity 결정
    ↓
BE 전달
```

예를 들어 안전모 미착용은 단일 프레임으로 바로 경고하지 않고, 지속시간과 신뢰도를 바탕으로 판단하도록 했다.

```text
helmet=false 1 frame
→ 무시

helmet=false 3초 지속
→ PPE_SUSPECT

helmet=false 5초 지속 + confidence > 0.8
→ PPE_VIOLATION

위험구역 내부 + PPE_VIOLATION
→ severity 상승
```

이때 프로젝트의 AI 파이프라인 가치는 단순 AI 호출 중계가 아니라, **모델 출력의 의미화와 판단 계층**에 있다고 보았다.

# 4. 초기 시연 환경 3단계 제안

초기에는 실제 건설현장을 반드시 확보하는 것을 MVP 성공 조건으로 두지 않고, 시연 환경을 3단계로 분리할 것을 제안했다.

```text
Level 1
Recorded / Public Dataset
        ↓
Level 2
Controlled Testbed
        ↓
Level 3
Real Construction Site
```

## 4.1 Level 1 — 개발 기준 환경

- 실제 또는 공개 건설현장 영상
- 자체 준비 영상
- Replay 기능을 통한 실시간 입력 흉내

예시:

```text
recording.mp4

09:00:03 normal
09:00:17 PPE violation
09:00:31 danger-zone intrusion
09:00:52 crack detected
...
```

Replay를 통해 AI부터 UI까지 전체 체인을 항상 재현할 수 있도록 한다.

## 4.2 Level 2 — 통제된 실환경(Testbed)

교실, 복도, 주차장, 야외 공간 등을 작은 건설현장처럼 구성하고 실제 사람이 다음 행동을 수행한다.

- 안전모 착용
- 안전모 제거
- 위험구역 진입
- 객체 방치
- 정상 작업

예시:

```text
CAM01
       Zone A
 ┌──────────────────┐
 │ 작업자 A          │
 │                  │
 │      위험구역     │
 │        ████      │
 │        ████      │
 │            작업자B│
 └──────────────────┘
```

실제 행동부터 시스템까지의 전체 체인:

```text
실제 행동
   ↓
카메라
   ↓
AI
   ↓
Pipeline
   ↓
Event
   ↓
Digital Twin 위치 변화
   ↓
경고
   ↓
Incident 저장
   ↓
Report
```

## 4.3 Level 3 — 실제 건설현장

실제 현장이 확보되면 연결하되 Core Requirement로 두지 않는 방향을 제안했다.

실제 현장은 다음 변수로 인해 프로젝트 일정 위험이 크다.

- 카메라 설치 허가
- 개인정보
- 작업자 촬영
- 네트워크
- 카메라 각도
- 안전 규정
- 현장 접근
- 공사 일정 변경

따라서 초기 제안에서는 다음 원칙을 제시했다.

```text
MVP 성공 조건
≠ 실제 공사현장에서 돌아간다

제품 확장성 검증
= 동일 Adapter를 실제 현장 소스로 교체할 수 있다
```

# 5. 초기 대표 시연 시나리오

초기에는 대표 시연 사건으로 다음을 제안했다.

> 작업자가 안전모 없이 통제구역에 진입한다.

전체 흐름:

```text
① CCTV 영상
        ↓
② Person Detection
        ↓
③ Helmet Detection
        ↓
④ Tracking
        ↓
⑤ Zone Mapping
        ↓
⑥ Pipeline 판단
   "PPE 미착용 + 위험구역"
        ↓
⑦ Event Queue
        ↓
⑧ BE 저장
        ↓
⑨ 2D/2.5D Digital Twin
   해당 Zone 강조
        ↓
⑩ 관리자 Alert
        ↓
⑪ Timeline 기록
        ↓
⑫ 보고서 생성
```

추가 이벤트 후보:

- 균열 / 구조 이상
- 작업자 또는 장비 위험구역 진입

모델 종류를 무작정 늘리는 것보다, 소수의 현실 이벤트가 전체 시스템을 관통하도록 만드는 것이 중요하다고 보았다.

# 6. 초기 의사결정 순서 제안

초기에는 다음 순서로 프로젝트 현실 연결부를 확정할 것을 제안했다.

1. 시연할 현실 사건 3~5개 확정
2. 각 사건에 필요한 원본 데이터(Source) 정의
3. 데이터 확보 방식 결정
   - 공개 데이터
   - 자체 촬영
   - 실시간 카메라
   - 합성
4. `Observation → Detection → Event → Incident` 계약 정의
5. AI 모델 담당과 Detection 출력 계약 체결
6. BE 팀장과 Event 입력 계약 체결
7. Replay / Simulation Adapter부터 구현
8. 통제 Testbed에서 End-to-End 검증
9. 실제 현장 확보 시 Adapter만 교체
10. Unreal / 3DGS 등은 동일 Event Contract를 소비

이 관점에서는 사용자 담당 영역을 다음과 같이 정의했다.

```text
          AI 담당
             │
        Detection
             │
             ▼
╔══════════════════════╗
║   사용자 담당 영역   ║
║                      ║
║ AI Pipeline          ║
║ Monitoring           ║
║ Validation           ║
║ Aggregation          ║
║ Event Engine         ║
║ Replay / Simulation  ║
╚══════════════════════╝
             │
           Event
             │
             ▼
          BE 팀장
```

초기 결론은 이 문제가 단순한 “어떤 데이터셋을 쓸까?”가 아니라, **현실 입력 계약과 제품의 증명 방법**이라는 것이었다.

# 7. 사용자 피드백: 초기 접근이 여전히 모호함

사용자는 위 접근에 대해 여전히 모호하다고 판단했다.

핵심 피드백:

> 데이터와 센서부터 정하는 것이 아니라, **실제로 이러한 현장 상태와 안전 관제를 담당하는 직무 자체를 먼저 분석**해야 한다.
>
> 해당 직무의 주요 업무와 실사용 툴을 조사한 뒤, 그 실제 업무 흐름에서 출발해 프로젝트를 이어나가야 한다.

이 피드백으로 인해 설계 출발점이 다음과 같이 변경되었다.

```text
기존:
기술 → 데이터 → 시연

수정:
직무 → 실제 업무 → 실사용 도구 → Pain Point → 필요한 데이터 → 자동화 → AI/관제 → 시연
```

# 8. 직무 기반 재정의

현장 상태 및 안전 관제와 관련된 실제 업무는 하나의 단일 직무가 아니라 여러 역할이 겹치는 형태로 정리했다.

| 역할 | 실제 책임 | 프로젝트와의 관계 |
|---|---|---|
| 안전관리자 | 위험성평가, 안전교육, 순회점검, 개선조치, 사고분석, 통계·기록 | 핵심 사용자(Primary Persona) |
| 관리감독자 / 공사 담당자 | 당일 작업 지휘, 설비·보호구 확인, 작업장 상태 확인, TBM | 현장 데이터 생산자 / 현장 조치 주체 |
| 스마트건설 / 안전관제 운영자 | CCTV·IoT·통신장비 운영, 관제센터 모니터링 | 시스템 운영자 |

핵심 해석:

- 안전관리자의 본업은 CCTV를 바라보는 것이 아니다.
- 실제 핵심은 **위험을 파악하고 → 조치시키고 → 결과를 기록하고 → 다음 위험관리로 연결하는 것**이다.
- 스마트 관제는 이 업무의 한 부분일 뿐이다.

따라서 프로젝트의 Primary Persona는 **안전관리자**로 잡고,
Secondary Persona는 **관리감독자 / 공사담당자**, 시스템 운영 측면에서는 **스마트 관제 운영자**로 보는 방향을 제안했다.

# 9. 실제 안전관리 업무 흐름

실제 안전관리 직무를 시간축으로 재배치하면 다음 구조로 정리할 수 있다고 보았다.

```text
[전날 / 작업 전]
명일 작업 확인
    ↓
작업 공종 / 인원 / 장비 확인
    ↓
위험성평가
    ↓
위험요인 + 감소대책 확정

[작업 직전]
TBM
    ↓
오늘 할 작업 전달
    ↓
오늘 위험요인 전달
    ↓
안전조치 확인

[작업 중]
현장 순회
    +
CCTV / IoT / 작업자 신고
    ↓
위험 발견
    ↓
관리자 판단
    ↓
작업중지 / 시정 / 전달
    ↓
조치 확인

[작업 후]
점검 결과
    ↓
위험 / 아차사고 / 사고 기록
    ↓
조치 이력
    ↓
안전일지 / 통계 / 보고
    ↓
다음 위험성평가에 반영
```

이를 하나의 업무 루프로 압축하면:

```text
계획
→ 위험 예상
→ 현장 전달
→ 실제 작업
→ 위험 관찰
→ 판단
→ 조치
→ 증빙
→ 재평가
```

이 세션에서 중요하게 본 지점은 다음이다.

> SENTIA가 자동화·보조해야 할 핵심 구간은 **실제 작업 → 위험 관찰 → 판단 → 조치 → 증빙** 사이이다.

# 10. 실제 현장의 실사용 도구

직무를 조사한 뒤, 현장이 첨단 시스템 하나로 통일된 것이 아니라 여러 도구가 혼재한다는 점을 중요하게 보았다.

대표적으로 다음이 동시에 존재할 수 있다.

```text
AI CCTV
+
IoT 센서
+
웨어러블
+
Excel
+
HWP
+
수기 점검
+
메신저
+
별도 관제 시스템
+
법정 / 공공 시스템
```

이 때문에 프로젝트의 경쟁 상대 또는 개선 대상은 단순히 “사람이 CCTV를 오래 보는 것”만이 아니다.

실제 Pain Point는 다음처럼 **업무 흐름이 여러 도구에 분절되는 것**으로 해석했다.

```text
현장
→ 엑셀 / HWP
→ 메신저
→ 별도 관제 시스템
→ 안전일지
→ 보고서
→ 법정 / 공공 시스템
```

즉, SENTIA의 가치 후보는 단순 “AI 탐지”보다 **분절된 안전 운영 흐름을 연결하는 것**에 있다.

---

# 11. 공공 / 법정 안전관리 시스템과의 관계

세션에서는 안전관리 업무가 이미 공공 시스템에 의해 일부 구조화되어 있다는 점도 반영했다.

## 11.1 KRAS

위험성평가 지원을 위한 시스템으로 다음과 같은 업무와 연결되는 것으로 정리했다.

- 위험요인 파악
- 위험성 결정
- 감소대책 수립
- 표준모델 / 체크리스트 활용

## 11.2 CSI

건설공사 안전관리 관련 정보망으로 다음 요소와 연결된다.

- 안전관리계획서
- 현장점검
- 아차사고
- 사고신고
- 사고사례
- 위험요소 프로파일
- 조치사항

이 관점에서 SENTIA가 법정 시스템을 대체하는 방향은 비효율적이라고 보았다.

대신 다음 구조를 제안했다.

```text
KRAS / 위험성평가
       ↓
SENTIA
       ↓
현장 실제 상태
       ↓
조치·이력 자동 축적
       ↓
CSI / 법정문서 / 사내보고에 쓸 데이터
```

즉, SENTIA는 **법정·행정 시스템의 앞단에서 실제 현장 상태와 조치 데이터를 구조화하는 운영 계층**이 될 수 있다.

# 12. 스마트 안전장비의 위치

세션에서는 스마트 안전장비를 크게 다음의 기능군으로 보았다.

| 분류 | 대표 기술 |

- 작업을 중지하거나 시정시키는가
- 조치 결과를 확인하는가
- 기록과 보고로 남기는가

이 간극이 SENTIA가 파고들 수 있는 핵심 영역으로 보였다.

# 14. 프로젝트의 출발점 재정의

```text
CCTV
 ↓
AI 모델
 ↓
이상 감지
 ↓
2D/3D 관제
 ↓
보고서
```

직무 중심 재정의:

```text
              [오늘의 작업]
                    │
         ┌──────────┴──────────┐
         ↓                     ↓
    작업계획                위험성평가
         │                     │
         └──────────┬──────────┘
                    ↓
              오늘의 위험 기준
                    ↓
──────────────────────────────────
                 실제 현장
──────────────────────────────────
     CCTV / 작업자 / 장비 / 센서
                    ↓
                AI 분석
                    ↓
        "현재 관측된 현장상태"
                    ↓
        ┌───────────┴──────────┐
        ↓                      ↓
   계획과 일치             위험/이상
                               ↓
                         관리자 확인
                               ↓
                     시정 / 작업중지
                               ↓
                          조치 확인
                               ↓
──────────────────────────────────
                 기록
──────────────────────────────────
        위험성평가 / 점검 / TBM
        일지 / 아차사고 / 보고서
```

핵심 제품 개념은 다음과 같이 재정의했다.

> **오늘 어떤 작업이 예정되어 있고 어떤 위험이 예상되며, 실제 현장에서 무엇이 벌어지고 있고, 발생한 위험을 누가 어떻게 조치했는지를 하나의 흐름으로 연결하는 안전 운영 시스템**

# 15. 직무에서 역산한 데이터 수집 설계

직무 중심으로 바꾸면서, 데이터 수집 역시 센서 종류가 아니라 실제 안전관리 질문에서 역산하도록 했다.

| 실제 업무 질문 | 필요한 데이터 | 최초 확보 방법 |
|---|---|---|
| 오늘 뭐 하는가? | 공종, 위치, 시간, 인원, 장비 | 일일 작업계획 |
| 오늘 뭐가 위험한가? | 위험요인, 위험도, 대책 | 위험성평가 |
| 누가 작업하는가? | 작업조 / 인원 | 출역정보 |
| 어디서 작업하는가? | Zone, 층, 작업구역 | 도면 |
| 지금 실제로 무슨 일이 있는가? | 영상 / 이미지 | CCTV |
| 장비는 어디 있는가? | 위치 / 상태 | CCTV 또는 IoT |
| 위험이 발생했는가? | AI Detection | AI 모델 |
| 실제 위험인가? | 지속시간 / 공간 / 작업 맥락 | AI Pipeline |
| 누가 조치했는가? | 담당자 / 조치내용 / 시간 | 모바일 / 웹 |
| 해결됐는가? | 완료상태 / 사진 / 확인 | 관리자 확인 |
| 무엇을 남겨야 하는가? | 이벤트 / 조치 이력 | 자동 기록 |

이 구조의 핵심은 **데이터부터 정하지 않고, 업무 질문 → 필요한 데이터** 순으로 정하는 것이다.

# 16. 사용자 담당 AI Pipeline 역할 재정의

직무 중심 구조에서도 AI Pipeline의 역할은 유지되지만, 의미가 더 명확해졌다.

AI 모델 담당의 출력 예시:

```text
frame
→ person
→ helmet=false
→ confidence .87
```

사용자 담당 AI Pipeline은 여기에 실제 작업 맥락을 결합한다.

```text
오늘 작업 = 철근 배근
작업 위치 = Zone B
위험성평가 =
  - 추락
  - 낙하
  - PPE

현재 시각 = 10:21
CAM-03 = Zone B

person #132
helmet=false
8.4 sec 지속
Zone B 내부
현재 실제 작업중
     ↓
PPE_VIOLATION 후보
     ↓
기존 동일 이벤트 확인
     ↓
중복 제거
     ↓
위험성평가와 연결
     ↓
안전관리자 확인 요청
```

따라서 사용자 담당 영역은 단순 중계가 아니라:

- AI Detection 수신
- 작업 맥락 결합
- 공간 정보 결합
- 지속성 판단
- 중복 제거
- 위험성평가와 연결
- 관리자 판단 요청
- Event 생성
- 이벤트 수명주기 관리

에 가깝다.

즉, **모델의 Detection을 실제 현장 안전업무에서 의미 있는 Event로 변환하는 계층**이다.

# 17. 직무 기반 시연 구조로 수정

초기 단순 시연:

> 작업자가 안전모를 벗는다 → AI가 잡는다.

이 시연은 객체탐지 데모에 가깝기 때문에 충분하지 않다고 재평가했다.

직무 기반 시연은 작업계획과 위험성평가부터 시작해야 한다.

## 17.1 작업 시작 전

```text
[09:00 작업 등록]

Zone B
- 철근 배근
- 작업자 4명
- 장비 1대

위험성평가
- PPE 미착용
- 중장비 접근
- 추락 위험
```

이후 TBM 화면에서 해당 위험요인을 확인한다.

## 17.2 실제 작업 중

```text
CAM03
 ↓
작업자 인식
 ↓
Zone B 매핑
 ↓
안전모 미착용 지속
```

## 17.3 관제 / 판단 UI

단순 경고:

```text
🚨 안전모 미착용
```

보다 다음처럼 실제 업무 맥락을 포함하는 UI가 적절하다고 보았다.

```text
Zone B / 철근 배근
10:24:31

예정 위험요인:
PPE 미착용

AI 관측:
작업자 #03
안전모 미착용 7.8초

CAM-03
신뢰도 91%

[확인] [현장조치 요청]
```

## 17.4 조치 과정

```text
10:25 조치 요청
10:27 현장 확인
10:28 안전모 착용 확인
        ↓
Incident CLOSED
```

## 17.5 작업 종료 후

```text
오늘 위험 이벤트       3
AI 감지                5
관리자 확인             3
오탐                   2
시정조치 완료           3
평균 조치시간          2m 14s
```

그리고 이 결과를 이용해:

- 일일 점검
- 안전업무 보고
- 조치 이력
- 위험성평가 피드백

등의 초안을 자동 생성할 수 있다.

이렇게 해야 시연이 **AI 모델 데모가 아니라 실제 안전관리 업무 전체 흐름의 데모**가 된다.

# 18. Digital Twin / 2D / 3D의 위치 재정의

직무 기반으로 보면 Digital Twin은 프로젝트의 목적이 아니다.

2D 도면은 가장 저렴하고 빠른 공간 표현이며, 다음과 같은 확장축을 갖는다.

```text
2D Floor / Zone
    ↓
2.5D
    ↓
BIM
    ↓
3D Digital Twin
    ↓
Unreal / 3DGS
```

즉:

- 2D / 2.5D는 현재 위치와 위험이 **어디서 발생했는가**를 보여주는 핵심 인터페이스
- BIM / Unreal / 3DGS는 같은 Event / Incident를 더 풍부한 공간 표현으로 시각화하는 확장팩

으로 정리한다.

Digital Twin은 목적이 아니라 **공간 표현 계층**이다.

# 19. AI의 위치 재정의

AI 역시 목적이 아니라 안전관리자의 감시·판단 부하를 줄이는 도구로 재정의했다.

```text
사람이 직접 계속 봐야 하는 현장
        ↓
AI가 선별
        ↓
사람이 판단
        ↓
시정
        ↓
증빙
```

즉, Human-in-the-loop 구조를 기본으로 한다.

AI가 최종 법적·운영상 판단자가 아니라:

- 관측
- 후보 이벤트 생성
- 이상 징후 선별
- 맥락 결합

을 수행하고, 실제 조치와 판단은 안전관리자가 수행한다.

# 20. 프로젝트 한 문장 정의 — 현재 세션 기준

직무 기반으로 프로젝트를 다음과 같이 재정의했다.

> **건설현장의 작업계획·위험성평가와 CCTV/IoT 기반 실제 현장 상태를 연결하여, 안전관리자가 위험을 빠르게 발견·판단·조치하고 그 결과를 자동으로 기록할 수 있도록 하는 경량형 스마트 안전 운영·관제 플랫폼**

핵심 구성요소는 다음과 같다.

```text
작업계획
+
위험성평가
+
현장 관측
+
AI 탐지
+
맥락 기반 Event 판단
+
관리자 조치
+
조치 이력
+
보고 / 기록
```

# 21. 기존 Reality Interface 접근에서 유지해야 할 것

직무 기반 재정의 이후에도 초기 제안 중 유효한 요소는 폐기하지 않는다.

유지 요소:

1. Adapter 기반 입력 추상화
2. Replay / Simulation 지원
3. Observation → Detection → Event → Incident 단계 분리
4. 실제 현장을 MVP 필수조건으로 두지 않음
5. 통제된 Testbed를 핵심 시연 후보로 유지 가능
6. 실제 현장 데이터와 공개 데이터 모두 동일 파이프라인에 넣을 수 있어야 함
7. Unreal / 3DGS는 동일 Event Contract를 소비하는 확장팩

다만 순서는 바뀐다.

```text
이전:
Source → Adapter → AI → Event → UI

현재:
업무 → 위험기준 → 필요한 관측 → Source → Adapter → AI → Event → 조치 → 기록
```

즉 Reality Interface Layer는 여전히 필요하지만, **직무 분석과 업무 계약에서 요구사항을 받은 뒤 설계되어야 한다.**

# 22. 현재 확정된 방향

본 세션 기준으로 다음은 방향성이 비교적 명확해졌다.

## 22.1 프로젝트 출발점

- 기술이 아니라 안전관리 직무
- AI가 아니라 업무 흐름
- 센서가 아니라 업무 질문

## 22.2 핵심 사용자

- Primary: 안전관리자
- Secondary: 관리감독자 / 공사담당자
- Operator: 스마트안전 / 관제 운영자

## 22.3 핵심 업무 루프

```text
계획
→ 위험 예상
→ 현장 전달
→ 실제 작업
→ 위험 관찰
→ 판단
→ 조치
→ 증빙
→ 재평가
```

## 22.4 핵심 제품 영역

특히 다음 구간:

```text
실제 작업
→ 위험 관찰
→ 판단
→ 조치
→ 증빙
```

## 22.5 AI의 역할

- Detection 생산 자체가 제품의 끝이 아님
- 작업 / 공간 / 시간 / 위험성평가 맥락과 결합
- 의미 있는 Event / Incident 후보로 변환
- 최종 판단은 관리자

## 22.6 공간 UI의 역할

- 2D / 2.5D가 MVP의 핵심 공간 인터페이스
- BIM / Unreal / 3DGS는 확장팩

## 22.7 문서화 / 보고의 역할

- 별도 부가기능이 아니라 업무 루프의 마지막 단계
- 이벤트와 조치 이력을 기반으로 자동화

# 23. 아직 미확정인 핵심 사항

직무 기반 방향은 잡혔지만, 다음은 아직 확정이 필요하다.

## 23.1 실제 업무 프로세스의 세부 분해

안전관리자의 실제 하루를 더 깊게 분해해야 한다.

예:

- 작업 전 회의

# 26. 세션에서 나온 핵심 문장 모음

본 세션의 의사결정을 압축하면 다음 문장들로 정리할 수 있다.

1. **문제는 데이터셋 선택이 아니라 현실과 시스템 사이의 연결부이다.**
2. **그러나 현실 연결부 역시 기술부터 설계하면 다시 모호해진다.**
3. **따라서 실제 안전관리 직무와 하루 업무 흐름에서 출발해야 한다.**
4. **안전관리자의 본업은 CCTV 관제가 아니라 위험의 파악, 판단, 조치, 기록이다.**
5. **현장은 AI CCTV, IoT, Excel, HWP, 수기, 메신저, 공공 시스템이 혼재한다.**
6. **SENTIA는 단순 대시보드보다 이 분절된 업무 흐름을 연결하는 쪽에 가치가 있다.**
7. **데이터는 센서 종류에서 고르는 것이 아니라 업무 질문에서 역산한다.**
8. **AI 모델은 Detection을 만들고, AI Pipeline은 실제 안전업무 의미가 있는 Event를 만든다.**
9. **최종 판단과 조치는 사람에게 남겨둔다.**
10. **2D / 2.5D Digital Twin은 목적이 아니라 공간적 상황 이해를 위한 인터페이스이다.**
11. **Unreal / 3DGS는 같은 Event Contract를 소비하는 확장팩이다.**
12. **시연은 객체탐지 데모가 아니라 작업계획 → 위험성평가 → 실제 현장 → 위험 감지 → 판단 → 조치 → 기록의 전체 업무 루프를 보여줘야 한다.**

# 최종 결론

이 세션에서 가장 큰 방향 전환은 다음이다.

초기에는 SENTIA의 미확정 문제를 **“현실 데이터를 어떻게 시스템에 연결할 것인가”**로 보았다. 이 접근에서 Reality Interface, Adapter, Replay, Testbed, Event Pipeline 같은 기술적 구조가 도출되었다.

그러나 사용자의 지적에 따라 더 근본적인 문제를 확인했다.

> **어떤 현실 데이터를 연결해야 하는지를 결정하려면, 먼저 실제 안전관리자가 어떤 일을 하고 어떤 도구를 쓰며 어디에서 불편을 겪는지를 알아야 한다.**

따라서 SENTIA의 현재 설계 원칙은 다음과 같다.

```text
직무에서 출발한다.
↓
업무를 분해한다.
↓
현재 사용 도구와 단절을 찾는다.
↓
보조할 업무를 선정한다.
↓
필요한 데이터를 역산한다.
↓
AI와 Pipeline을 배치한다.
↓
관제 UI와 공간 표현을 붙인다.
↓
실제 업무 루프 전체를 시연한다.
```

이 문서가 현재 세션의 정본이며, 이후 데이터 수집·시연 환경·AI Pipeline·2D/2.5D 관제·Unreal/3DGS 확장 설계는 이 문서를 기준으로 이어간다.
